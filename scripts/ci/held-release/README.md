# Held release rehearsal for EverywherePoster #368

This package rehearses an application restart with publishing paused. It deliberately limits availability to sign-in, static assets, and session identity. `launch.sh` runs the packaged frontend and backend with the orchestrator absent and rejects a set `RUN_CRON` variable, enabled registration, or enabled MCP before startup. `ingress.py` binds only to loopback and permits a fixed set of paths and methods. It stops accepting new requests before waiting for in-flight requests to finish. `verify.py` runs solely against owned disposable Docker resources.

The launcher and ingress gate are 156 lines. The remaining code builds isolated fixtures and exercises both image versions, drain and recovery through the same boundary. Keeping the harness with the launcher avoids a separate unreviewed registry export or a production test.

## Run and read the evidence

- The in-repository `Pinned held PC release rehearsal` check uses only the named same-repository draft branch. A hosted job pulls the two private packages with its read-only token, removes registry authorization, and executes the test with synthetic credentials on an internal Docker network. The runner never publishes app ports or calls production.
- The phase order is prior image on the upgraded schema, candidate image, and prior-image rollback on that same upgraded schema. Each phase exercises a fresh login and authenticated identity, blocks publishing and other mutation routes, observes the running processes, and drains an actual admitted request while refusing another. The launcher then receives SIGTERM and must exit cleanly. The fixture rejects any Temporal workflows or inserted post/receipt rows and verifies the migration ledger survives recovery.
- The current PC development engine can run a candidate-only check with `python3 -B scripts/ci/held-release/verify.py --candidate-only`. That does not qualify rollback or prior startup. Full verification requires both exact published images and uses `python3 -B scripts/ci/held-release/verify.py` in the hosted job.

## PC production gate

The PC release operator and independent reviewer must still bind an authenticated running-only production control channel, or verify an existing persistent publishing hold before a controlled boot. A Linux Unix socket can provide peer authentication only to a caller already reaching that guest. No verified Windows-to-production Unix socket bridge or existing authenticated equivalent has been established. The earlier WSL list, command, system-view and UNC tests do not supply admission.

Before execution, bind the exact launcher and ingress rule set to the PC rootless network and its production TLS/cookie settings. Independently qualify both held images and their recovery under those conditions. The fixture's loopback HTTP gate and synthetic auth flags are test machinery. Verify that provider egress and any bypass of the intended ingress are blocked, and that the live app and workers have settled before backup. Confirm actual PostgreSQL identity, the sole pending checksum, a fresh encrypted backup, and its successful isolated restore. Keep the publishing hold persistent through any failure and keep prior-image recovery available. Neither success nor fallback may start the old or candidate orchestrator. The known Temporal replay incompatibility is a separate gate to any future publishing resumption.
