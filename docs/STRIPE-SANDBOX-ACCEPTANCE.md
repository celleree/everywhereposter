### Accounting contract

Under organization wallet lock namespace 3, aggregate `heldNanos` must equal the sum of RESERVED/DISPATCHED/UNKNOWN reservation ceilings plus REQUESTED refund amounts. SETTLED reservations (including zero-cost settlement) and RELEASED reservations hold zero, regardless of their original ceiling. WITHDRAWN/REJECTED requests hold zero. An unexpected state, charged active reservation or mismatched aggregate fails closed; it is not automatically repaired. Request eligibility additionally requires FUNDING minus USAGE to equal balance and an ACTIVE wallet. Unknown provider results retain their full current hold. Existing receipt settlement and lock-2 current-plan dispatch authorization remain intact.

One helper applies this invariant to new spending, dispatch, settlement, cancellation and request mutation. Balance display reports REVIEW and zero available value on inconsistent holds; request summary reports zero eligibility. A terminal release can proceed on an otherwise reconciled REVIEW wallet without changing its REVIEW status, usage holds or balance. A repeated terminal operation reads its original result without releasing value again.

### Approved non-financial API

| Route | Authority / behavior |
| --- | --- |
| `GET /billing/ai-wallet/refund-requests` | Authenticated current-organization member; its summary and most recent 20 requests |
| `POST /billing/ai-wallet/refund-requests` | Current organization billing ADMIN/SUPERADMIN; server-calculated eligibility, `{operationKey}` only |
| `POST /billing/ai-wallet/refund-requests/:id/withdraw` | Current organization billing ADMIN/SUPERADMIN; only that organization's pending request |
| `GET /billing/ai-wallet/refund-review?cursor=...` | Existing platform `user.isSuperAdmin` authority only; up to 100 pending records and `nextCursor` |
| `POST /billing/ai-wallet/refund-review/:organizationId/:id/reject` | Existing platform `user.isSuperAdmin` authority only; explicit target organization and request identity |

The only transitions are REQUESTED -> WITHDRAWN and REQUESTED -> REJECTED. A request ID plus terminal outcome identifies a terminal operation; retrying it returns the same durable actor, timestamp and result. An opposing outcome is a conflict. Replaying the original creation key returns that request, including its terminal result; a new request requires a new key. Creation identity, amount, organization, actor and timestamp are immutable; terminal outcome/actor/time are retained. SQL constraints and a history guard reject deletion and mutation of resolved records. The ledger, balance and provider state are never changed by these transitions. The exact request hold is released atomically once under the spend lock. Request access and release survive subscription revocation and disabled billing flags; recovery never resurrects released requests.

The review cursor contains `(createdAt, id)` and uses ascending keyset ordering, independently of whether the cursor row remains pending. Equal timestamps and resolution between pages cannot strand records after the first 100. There is no approval, completed refund, payment, automatic expiry or dispute outcome state. This slice exposes backend APIs only; it does not import or activate the original checkpoint's customer UI.
