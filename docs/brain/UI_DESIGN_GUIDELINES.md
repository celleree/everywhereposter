# EverywherePoster UI Design Guidelines

Updated: 2026-11-22
Scope: EverywherePoster product UI and related design reviews. This is **project context for expert design skills**, not a competing design skill or a report that every screen already meets these standards.

## How to use this file

For a UI task, read this file alongside the affected rendered screen and owning components. Use a maintained expert skill (such as Impeccable for critique/polish or a frontend-design skill for new layouts) for the **method**; this file supplies **EverywherePoster-specific constraints**. Do not copy, fork, or rewrite the expert skill just to embed these guidelines.

Apply the repository's source-of-truth rules in `AGENTS.md`. In particular:
- Current component/CSS/config and tests establish what is implemented; this document does not overrule runtime facts.
- `docs/brain/PRODUCT_TRUTH.md` governs product promises and supported workflows.
- The user's current approved task defines the desired change; protect unrelated established behavior.
- `docs/brain/EVERYWHEREPOSTER_UI_IMPROVEMENTS.md` records concrete user-approved UX decisions for the documented batch; do not assume every item has shipped or generalize its exceptions to unrelated screens.
- `docs/browser-acceptance.md` governs the applicable UI/browser verification and its limitations.

The former custom Publish Everywhere design-engineer skill is **not** an authoritative product or design source. Its video-only assumptions, global glass/prism preference, and default recommendation to introduce UI libraries must not supersede this repository.

## Product and interaction direction

- The product is **EverywherePoster**, a source-content-first repurposing and distribution app, not a video-only creator or a generic social scheduler. The source can be video, image, or text where the implemented flow supports it.
- Make the shortest understandable path through source selection, destination selection, review and publish/schedule. Preserve explicit confirmation/control for consequential publishing; remove redundant confirmation/navigation only when the approved workflow permits it.
- Prioritize fast comprehension, low cognitive load, and preservation of in-progress work over decoration. One control should own each decision: avoid repeated account selectors, version navigation, duplicated headings, summary cards, and excess advanced options.
- Show platform-specific controls only where relevant to selected destinations. Keep essential context and a clear next action visible.
- Never turn media attachment or destination switching into unrequested preview/autoplay. Make preview a distinct deliberate action.
- Show actual processing status, errors, retry/recovery and persistence honestly; never invent progress, success, analytics, or completed publishing.
- Design for users with many connected accounts, long names, multiple assets, empty libraries, failed integrations, and partial results, not just the demonstration account.

## Existing visual system (inspect before changing)

The application's implemented light/dark theme and component treatments are the starting point, not arbitrary colors generated by a skill.

- Source theme tokens: `postiz-app/apps/frontend/src/app/colors.scss`; Tailwind mappings: `postiz-app/apps/frontend/tailwind.config.cjs`; global styles: `postiz-app/apps/frontend/src/app/global.scss`; mobile layout: `postiz-app/apps/frontend/src/app/mobile-ui.scss`.
- Representative **dark** token values: `--new-bgColor: #08080a`, `--new-bgColorInner: #101014`, `--new-border: #27272f`, `--new-textColor: 244 244 245`, `--new-textItemBlur: #a1a1aa`, `--new-ai-btn: #22d3ee`.
- Representative **light** token values: `--new-bgColor: #fafafa`, `--new-bgColorInner: #ffffff`, `--new-border: #e4e4e7`, `--new-textColor: 9 9 11`, `--new-textItemBlur: #71717a`, `--new-ai-btn: #0891b2`.
- These values are **examples of current implementation**, not a second hard-coded palette. Use existing semantic variables/classes; never introduce a parallel palette for the same roles. Avoid deprecated `--color-custom*` variables in new work.
- Favor the actual local component vocabulary for forms, buttons, cards, drawers, headers, navigation and messages. Inspect neighboring screens for typography scale, density, spacing, borders, radii and interaction states before designing replacements.
- The app layout imports `Plus_Jakarta_Sans`, while Tailwind `fontFamily.sans` names `Helvetica Neue`; font usage is **not yet reconciled into a single verified typography specification**. Inspect computed styles and the owning components before asserting or changing the default.
- Use consistent, restrained surfaces; a compact functional app is not a cinematic landing page. Preserve any approved marketing hero/visual identity separately; do not force glass, glows, prism effects or 3D onto composer and dashboard controls.
- Keep existing branding and asset paths. Do not rebrand, redesign the marketing site, or replace logos as a side effect of general UI polish.

## Layout, states and accessibility

- Establish clear page, section, label and action hierarchy. Use a repeatable spacing rhythm and coherent radii **derived from the existing components**, rather than inventing unverified global numeric tokens.
- Avoid wasted above-the-fold space and unnecessary nested scrolling. Allow scrolling where content genuinely exceeds the viewport; keep dialogs, media previews and close controls fully reachable without horizontal page scroll.
- On phones, account for safe areas, keyboard focus, bottom navigation, touch targets, long text and varying viewport heights. Desktop, tablet and narrow mobile need layouts that work, not just scaled screenshots.
- Every changed flow must handle loading, empty, success, error, disabled and recovery states where applicable. Preserve draft or input state across accidental navigation/reload when the current flow promises persistence.
- Preserve keyboard and screen-reader semantics, readable contrast, visible focus, form labels and non-color-only state feedback. Respect reduced-motion preferences. Existing `global.scss` includes a broad `outline: none !important` rule; inspect actual focus treatment rather than assuming it is accessible.
- Use purposeful motion sparingly. Motion must not hide primary actions, delay comprehension, shift layout, or make the application feel slower.

## Expert-skill implementation and verification contract

1. Identify the screen, user task, component owners, product constraints and applicable existing patterns. Do not audit or rewrite the whole application for a bounded task.
2. Ask the expert skill for a clear hierarchy/layout and concrete critique **within the constraints above**; reject suggestions that require unsupported product behavior, an unrelated redesign or new UI dependencies by default.
3. Implement the smallest coherent change. Follow `postiz-app/CLAUDE.md` and `AGENTS.md`; in particular, use native components and do not add frontend component packages without explicit approval.
4. Render the changed UI, inspect screenshots at representative desktop/tablet/phone widths, and compare dark/light themes where relevant. Check real content, long names, empty/error/processing states, keyboard focus and touch/viewport behavior.
5. Run focused tests and the applicable Playwright/browser checks in `docs/browser-acceptance.md`. Fix demonstrated visual/behavior defects, then rerender and recheck. Limit ordinary polish loops rather than repeatedly redesigning a completed screen.
6. Report the exact screens examined, visible issues corrected, tests/evidence, and any unverified states. Automated or emulated checks do not by themselves prove physical-device or deployed behavior.

## Maintenance rules

- Edit this file only for **durable** product-wide design decisions verified against current code, approved UI direction and representative screens. Put one-off screen requirements in their task/issue, not here.
- Do not turn a preferred numerical spacing/radius/font choice into a rule until it has been reconciled with existing code and intentionally approved.
- Keep the expert skill independently updatable. This project file should be a portable reference that any design agent can read.
- When product/UI rules change, update the relevant canonical source and this file in the same bounded reviewed change. Do not preserve stale instructions solely because they appeared in an older skill.
