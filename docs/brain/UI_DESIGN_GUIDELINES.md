# EverywherePoster UI Design Guidelines

Updated: 2026-11-23
Scope: EverywherePoster product UI and related design reviews. This is **project context for expert design skills**, not a competing design skill or a report that every screen already meets these standards.

## How to use this file

For a UI task, read this file alongside the affected rendered screen and owning components. Use a maintained expert skill (such as Impeccable for critique/polish or a frontend-design skill for new layouts) for the **method**; this file supplies **EverywherePoster-specific constraints**. Do not copy, fork, or rewrite the expert skill just to embed these guidelines.

Apply the repository's source-of-truth rules in `AGENTS.md`. In particular:
- Current component/CSS/config and tests establish what is implemented; this document does not overrule runtime facts.
- `docs/brain/PRODUCT_TRUTH.md` governs product promises and supported workflows.
- The user's current approved task defines the desired change; protect unrelated established behavior.
- `docs/brain/EVERYWHEREPOSTER_UI_IMPROVEMENTS.md` records concrete user-approved UX decisions for the documented batch; do not assume every item has shipped or generalize its exceptions to unrelated screens.
- `docs/browser-acceptance.md` governs the applicable UI/browser verification and its limitations.

The former custom Publish Everywhere design-engineer skill is **not** an authoritative product or design source. Its video-only assumptions, global glass/prism preference, and default recommendation to introduce UI libraries must not supersede this repository.

## Product and interaction direction

- The product is **EverywherePoster**, a source-content-first repurposing and distribution app, not a video-only creator or a generic social scheduler. The source can be video, image, or text where the implemented flow supports it.
- Make the shortest understandable path through source selection, destination selection, review and publish/schedule. Preserve explicit confirmation/control for consequential publishing; remove redundant confirmation/navigation only when the approved workflow permits it.
- Prioritize fast comprehension, low cognitive load, and preservation of in-progress work over decoration. One control should own each decision: avoid repeated account selectors, version navigation, duplicated headings, summary cards, and excess advanced options.
- Show platform-specific controls only where relevant to selected destinations. Keep essential context and a clear next action visible.
- Never turn media attachment or destination switching into unrequested preview/autoplay. Make preview a distinct deliberate action.
- Show actual processing status, errors, retry/recovery and persistence honestly; never invent progress, success, analytics, or completed publishing.
- Design for users with many connected accounts, long names, multiple assets, empty libraries, failed integrations, and partial results, not just the demonstration account.

## Existing visual system (inspect before changing)

### Brand color identity — locked

Keep EverywherePoster's established **black-and-white / neutral grayscale identity** in both light and dark modes. Blacks, whites and neutral grays are the design palette; do not introduce new brand colors, gradients or colorful UI themes because an expert design skill recommends them. Existing functional/provider-specific accents are exceptions only where already implemented and needed; they are not permission to invent a new general accent palette. Do not change approved brand colors without an explicit product-design decision.

The application's implemented light/dark theme and component treatments are the starting point, not arbitrary colors generated by a skill.

- Source theme tokens: `postiz-app/apps/frontend/src/app/colors.scss`; Tailwind mappings: `postiz-app/apps/frontend/tailwind.config.cjs`; global styles: `postiz-app/apps/frontend/src/app/global.scss`; mobile layout: `postiz-app/apps/frontend/src/app/mobile-ui.scss`.
- Representative **dark** token values: `--new-bgColor: #08080a`, `--new-bgColorInner: #101014`, `--new-border: #27272f`, `--new-textColor: 244 244 245`, `--new-textItemBlur: #a1a1aa`, `--new-ai-btn: #22d3ee`.
- Representative **light** token values: `--new-bgColor: #fafafa`, `--new-bgColorInner: #ffffff`, `--new-border: #e4e4e7`, `--new-textColor: 9 9 11`, `--new-textItemBlur: #71717a`, `--new-ai-btn: #0891b2`.
- These values are **examples of current implementation**, not a second hard-coded palette. Existing cyan AI-action tokens and provider/status colors are established exceptions to the black-and-white base, not a new brand direction. Use existing semantic variables/classes; never introduce a parallel palette for the same roles. Avoid deprecated `--color-custom*` variables in new work.
- Favor the actual local component vocabulary for forms, buttons, cards, drawers, headers, navigation and messages. Inspect neighboring screens for typography scale, density, spacing, borders, radii and interaction states before designing replacements.
### Typography — preserve, do not invent

- **Primary application typeface: Plus Jakarta Sans.** The app's `(app)/layout.tsx` applies the Next.js `Plus_Jakarta_Sans` class to `body`; `src/components/new-layout/layout.component.tsx` also applies it to the application shell. The layout loads 500/600 weights and the shell configuration additionally includes 700. Preserve this current primary typeface and its existing typography hierarchy. Do not substitute Inter, Geist, serif headlines or another skill's default typeface.
- **Legacy/special-case typeface: Helvetica Neue.** `tailwind.config.cjs` sets `fontFamily.sans` to `Helvetica Neue`, and `global.scss` has an explicit `.set-font-family` override. Preserve those existing usages unless a separately approved typography cleanup establishes how to unify them.
- Keep the existing readable hierarchy and distinguish page titles, section titles, labels, helper text and content according to surrounding app components. An expert may improve weight, scale and text balance within the established typefaces, but must not change the font family or product-wide hierarchy arbitrarily.
- This is a **code-based inventory**, not a verified computed-style audit of every screen. Inspect rendered text before altering a special-case component.

### Corner radii — preserve the existing vocabulary

Current frontend styles show several intentional radii rather than one universal value:
- **8px** is used for form/tag inputs (examples in `global.scss`).
- **10px** is used for multiple buttons and form surfaces in `mobile-ui.scss`.
- **12px** is used for composer cards, textareas and the main application shell.
- **16px** is used for the mobile bottom-navigation container.
- **18px** is used for the mobile More drawer's top corners.
- **Full circles/pills** are used where controls or badges are explicitly circular.

These are observed, role-dependent precedents, **not an instruction to use every value on every screen**. Match existing components of the same role. Unify a demonstrably inconsistent corner treatment within a bounded change, but do not invent a new global radius scale or randomly make every element rounder/squarer. No new product-wide radius system without an explicit approved decision.
- Preserve the functional application's established surfaces and identity; a marketing landing-page treatment is not automatically an app-wide style rule. Expert designers may improve visual hierarchy, interaction styling and motion within the approved monochrome palette and type system; don't transfer glass, prism or 3D motifs from an old custom skill by default.
- Keep existing branding and asset paths. Do not rebrand, redesign the marketing site, or replace logos as a side effect of general UI polish.

## Layout, states and accessibility

- Establish clear page, section, label and action hierarchy. **Spacing and component dimensions are intentionally flexible**: let the expert skill improve density, rhythm and sizing for the task. Preserve the established typography and role-appropriate corner-radius vocabulary above.
- Avoid wasted above-the-fold space and unnecessary nested scrolling. Allow scrolling where content genuinely exceeds the viewport; keep dialogs, media previews and close controls fully reachable without horizontal page scroll.
- On phones, account for safe areas, keyboard focus, bottom navigation, touch targets, long text and varying viewport heights. Desktop, tablet and narrow mobile need layouts that work, not just scaled screenshots.
- Every changed flow must handle loading, empty, success, error, disabled and recovery states where applicable. Preserve draft or input state across accidental navigation/reload when the current flow promises persistence.
- Preserve keyboard and screen-reader semantics, readable contrast, visible focus, form labels and non-color-only state feedback. Respect reduced-motion preferences. Existing `global.scss` includes a broad `outline: none !important` rule; inspect actual focus treatment rather than assuming it is accessible.
### Motion and interaction feel — creative freedom

- Aim for **satisfying, natural, responsive, expressive animation** across the application. Rich motion, spring dynamics, gesture responses, smooth transitions, animated state changes and more ambitious interactions are welcome when an expert motion/design skill judges them beneficial.
- **Do not impose arbitrary caps** on animation count, duration, complexity, intensity or style; remove defaults such as "subtle", "sparse", "fast only" or "use animation only when strictly necessary". Let the expert skill choose the motion approach from the task and its visual critique.
- Motion may add delight and polish even when it is not strictly required to explain a feature. Judge it by how natural, satisfying and coherent the interaction feels, not by a minimum-animation rule.
- Animation must still preserve correct actions, reachable controls, understandable feedback, reliable performance and support for reduced-motion accessibility preferences. Those are functional quality requirements, not blanket aesthetic limits. Never trigger publishing or media playback without the user's action.

## Expert-skill implementation and verification contract

Use the installed expert design skill's **own** critique, audit, animation, visual review and refinement methods. Do not duplicate its teaching, impose a homemade aesthetic checklist, or restrict its creative process. For example, Impeccable provides `critique`, `audit`, `animate`, `delight` and `overdrive` methods; its documentation describes rendered-page checks as well as code pattern checks.

The repository's minimum outcome requirements still apply, because merely loading a skill does not execute browser validation:
1. Scope the task to the affected screen and preserve this file's brand, typography, radii, UX contracts and repository instructions.
2. Implement with existing native components and approved dependencies; use the expert skill's preferred design/motion approach within those constraints.
3. **Verify the actual rendered result**, not just the source: use the skill's available review tools and inspect applicable desktop/mobile, light/dark, interaction, empty/error and animated states. Follow the applicable browser/Playwright requirements in `docs/browser-acceptance.md`.
4. Fix demonstrated visual or behavior defects and verify the changes again. Report evidence and unverified cases. Do not claim that a code-only audit is a full visual test, or that emulation proves physical-device behavior.

The expert skill determines **how** to perform professional visual inspection; this file requires only an observable result and truthful verification record.

## Maintenance rules

- Edit this file only for **durable** product-wide design decisions verified against current code, approved UI direction and representative screens. Put one-off screen requirements in their task/issue, not here.
- Do not impose new mandatory spacing/component dimensions. Preserve the documented font families, monochrome identity and role-specific radius precedents; broad changes to those identities require a deliberate product decision.
- Keep the expert skill independently updatable. This project file should be a portable reference that any design agent can read.
- When product/UI rules change, update the relevant canonical source and this file in the same bounded reviewed change. Do not preserve stale instructions solely because they appeared in an older skill.
